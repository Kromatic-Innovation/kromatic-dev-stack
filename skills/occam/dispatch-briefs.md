# Occam — Fanout & Dispatch-Brief Rules

Companion to `occam/SKILL.md` Gate 3. Read before spawning any implementation lane. Rules only — the incident history that justified each rule lives in your retro log, not here.

## Lane basics

- **Every implementation lane gets a dispatch brief — single-repo included.** Gate 3 mandates delegation for all implementation work, not just multi-repo fanouts; a one-file, one-repo fix still needs a brief, a closure-mode declaration, and the same contract below. The only inline exception is a mechanical nit in a file the current lane already has open (see Gate 3).
- One worker lane per repo issue. Repo-local ownership; no mixed-repo commits.
- Worker lanes are blocked until the assigned issue exists and dependencies are unblocked.
- **Session-budget rule (multi-phase epics):** epics with 5+ child issues or spanning 2+ repos plan session chunk boundaries in the epic issue body; target 3-4 issues per session to stay within context-window limits; enumerate cross-repo dependencies per phase (which repos each phase touches). When an epic body lacks chunk boundaries, add them before fanout.

## Dispatch-brief contract (every implementation lane)

- **Model per work class (required — cite your model-routing guidance):** every brief sets an explicit `model` on the Agent-tool call per the v1 routing table in your model-routing guidance — do not let a worker silently inherit the session's model. Any downgrade below that table's floor requires evidence per that doc's evidence rule (cost-to-mergeable ledger number or a shadow study), not a default assumption that a fanned-out worker should match the orchestrator's own model tier.
- **Declared `target_repo` (required — an internal issue):** every brief names the lane's target repo as `target_repo: <owner/repo>`. When the lane is dispatched with Agent `isolation: "worktree"`, the orchestrator surfaces that value to the `WorktreeCreate` hook by exporting `WORKTREE_TARGET_REPO=<owner/repo>` for that dispatch. The hook then **refuses** to cut a worktree whose session-repo origin differs from the declared target — it would fork the worktree from the wrong repo and the lane's target file would not exist (the dispatch-briefs.md:139 failure, which was read in-session and violated anyway). This is a gate, not prose: see "Worktree isolation → Cross-repo gate" below. A same-repo lane may set it harmlessly (it matches); a lane that omits it keeps working (the gate is permissive when no target is declared).
- **Action-biased briefs:** state the goal, name the specific files to edit, and include an explicit *"be action-biased: read minimally, edit directly — do not spend more than a few minutes reading."* Constrain orientation to one or two targeted reads before the first edit, not a full repo sweep. Implementation agents have a finite stream-idle budget; a long read-heavy phase can burn it before a single edit lands.
- **No agent-armed auto-merge:** the brief instructs `gh pr create` only; the agent does NOT run `gh pr merge --auto` (with or without `--merge`/`--squash`). The orchestrator owns merge timing because Quine review and the QA triage gate must run on a non-merging PR. Brief language: *"Do NOT enable auto-merge. Open the PR with `gh pr create --base develop ...`, then emit your completion report with the PR URL and CI state. The orchestrator owns Quine review, triage, and the final merge."*
- **No agent-spawned CI pollers:** the brief instructs the agent to emit its completion report immediately after `gh pr create` (PR URL + current CI state via one `gh pr view`), then exit. No background poller, no CI loop, no "still polling" exit. Brief language: *"After `gh pr create`, emit your completion report with the PR URL and current CI state (one `gh pr view`). Do NOT spawn a background poller, loop on CI, or exit with a 'still polling' message — the orchestrator owns CI polling, Quine review, and merge timing."*
- **No background-and-exit (subagents are never woken):** background-task completion notifications go to the orchestrator's turn loop, not to a completed subagent — a lane that launches a long build/test as a background task and ends its turn "awaiting the wake-up" simply dies mid-pipeline, and its detached processes may be killed with it. There is no SendMessage path to resume it. Brief language: *"Do NOT background long builds or test runs and exit expecting a completion wake-up — WAIT for them in-turn with generous timeouts; only finish your turn after the PR exists or you are truly blocked."* (Bit two lanes in one session; the lane briefed with this line completed cleanly.) Orchestrator-side waits are the opposite: the orchestrator DOES get notified, so it should background long waits freely.
- **Foreground verification (mid-lane commands, not just the end-of-turn case above):** the "subagents are never woken" mechanism in the bullet above applies to every blocking verification command a lane runs, not only a lane's final build/test before reporting done. Never background a command whose result you are waiting on and then end your turn — you will not be notified when it finishes; only the orchestrator receives async task-notifications, and only for agents *it* spawned. Run test suites, builds, and other long-running checks as plain synchronous/foreground calls and read the real output in the same tool call before proceeding or reporting done. Brief language: *"Run blocking verification commands (test suites, builds, long-running checks) in the foreground — do not background them and wait for a notification; you will not receive one."* (Three dispatched lanes stalled on this exact pattern in one session — three separate lanes, 2026-07-27 — each requiring an orchestrator resume to re-run the command synchronously; costly on an internal issue where the fix was urgent.)
- **No ending the turn on a pending CI or async-review check:** a lane may not end its turn while a required CI check OR an async-review bot (`claude-review`, Seer, Codacy) is still `pending` — reporting "waiting for claude-review to finish" and stopping is a background-and-exit violation even when the required CI checks have already passed. Poll `scripts/gh_wait_status.sh ... --json` (it blocks) to a terminal CI state, then poll `gh pr checks <PR#>` until every async-review bot has left `pending`, and only then emit the ready-green report or a named blocker. This does not conflict with the context-budget handoff rule below, or with `SKILL.md`'s `/loop` (ralph-loop) guidance for long CI waits that would exceed the context window — the rule here is against *silently* exiting mid-wait, not against blocking or handing off.
- **Delegate PR/merge/promotion monitoring to a dedicated watcher sub-agent (recommended):** rather than polling CI/merge/promotion inline in your own long-running context — where the rule above is observed to fail in practice (stalling on a check that was never required, or missing a bot comment that flagged something real) — dispatch a narrow sub-agent whose sole job is to watch one PR to a terminal, actionable state and report `proceed`/`escalate`. Back it with a deterministic status script rather than model judgment: the script should **filter CI-terminal to branch-protection-REQUIRED contexts only** (so a decorative check that hangs never wedges the wait) and **read async-review-bot review/comment CONTENT** (not just check-run status), pre-classifying each finding as actionable `true`/`false`/`"unknown"`. If your harness supports a stop-hook, use it to block the sub-agent from ending its turn while the script still reports "waiting" — that enforces the wait contract structurally rather than by the model remembering this prose. The sub-agent's one judgment call is reading any `"unknown"` bot finding and deciding `proceed` vs `escalate`; it does not edit code, merge, or promote — it reports, and you act. Isolating monitoring in a narrow sub-agent avoids the context-drift failure mode a multi-hour orchestrator session is prone to.
- **Closure-mode declaration (required — no silent default; v2 flips the default):** every brief states which mode applies:
  - `CLOSURE-MODE: OWN-FULL-PIPELINE` (**default for every lane**): staging promotion is the default goal, not an opt-in. The agent runs the full Ship-to-staging routine itself (CI wait, merge, develop CI, staging promotion, staging CI, follow-up issue filing, retro) — or, for a repo you have marked batched-promotion, stops at develop-green (the orchestrator batches that repo's staging promotion separately; see "Batched-promotion repos" below). Pair with a scope check — if the lane exceeds its authorized scope mid-run, revert to STOP-AT-PR semantics and hand off.
  - `CLOSURE-MODE: STOP-AT-PR` (**opt-in — the orchestrator must declare it explicitly** in the brief for lanes it deliberately wants to gate between PR-open and merge: async-review dependencies, high-blast-radius changes, or any lane sharing a base with a sibling lane awaiting sequential-merge ordering): the agent reports the PR URL + one CI snapshot and exits; the orchestrator owns merge timing, Quine dispatch, and post-merge gates.
  - **Escalate-or-finish (no silent early exit):** whichever mode applies, the agent either reaches its contracted gate (PR ready, or merged+staged per OWN-FULL-PIPELINE, or develop-green for a `batched` repo) OR emits a completion report naming the exact blocker before ending its turn. Silently stopping short of the gate with no blocker named is never acceptable — brief language: *"Reach the contracted gate or tell me exactly what's blocking you. Do not end your turn with partial progress and no named reason."*
  - **Sequential-merge rule (stated in every brief, all operators):** *"Before merging into `develop` (or any shared base), run `gh pr list --base <base> --state open --json number,autoMergeRequest` — if a sibling lane's PR is CLEAN-and-arming or already merging into the same base, wait for it to land (`state == MERGED`) before your own merge. Never arm parallel merges into the same base without orchestrator-confirmed ordering; the orchestrator, not the worker, decides merge order across sibling lanes."* (Full rationale: "Parallelism & merge ordering" below.)

  **Batched-promotion repos:** when staging runs are expensive for the target repo, mark it batched — OWN-FULL-PIPELINE's ceiling becomes develop-green, not staging. The brief states this explicitly: *"This repo batches staging promotion — stop after merge-to-develop and develop-CI-green; do not promote to staging yourself. The orchestrator runs one staging promotion pass across all batched repos once the day's lanes are green."* Repos that promote immediately (the default) promote to staging per-lane as part of OWN-FULL-PIPELINE.
- **Verify-by-running observation (required in the completion report when the lane has a behavioral surface):** the closure contract does not accept "tests pass" as evidence a behavioral change works. When a lane changes behavior with a runtime surface, its completion report MUST record HOW that behavior was observed: the affected flow *driven locally* via the `verify` / `run` skill, *covered by the Ship-to-staging Playwright E2E gate* (heavy / multi-service repos — GATE 4 / GATE 6), or an *explicit one-line statement of why neither was possible*. This distinguishes *driving the real flow* from *running the test suite* — per the `verify` skill's framing, `npm test` is not "running the repo." A no-runtime-surface lane (pure skill-doc/config, or a library/engine with no caller) is exempt from the run; a no-caller engine instead trips the inert-component flag. Full grading + the hard line: `occam/verify-by-running.md` (Gate 3).
- **Context-budget handoff (briefs >~100 LOC across 3+ new files, or shared-infra rebases):** include *"Budget your context. Once you have a green PR open, if you suspect you're running low on context, STOP and emit a completion report with: PR URL, CI status, what's left (typically wait-for-CI, merge, cleanup). The orchestrator will take the handoff. A clean mid-pipeline handoff beats a truncated report."*
- **Verification-account hygiene:** when a brief asks a lane to exercise a self-registration, self-signup, or agent-signup flow end-to-end (e.g. `/auth/agent-signup`-style endpoints) as part of verify-by-running, the brief MUST specify an owned `+test` email alias for the lane to use (matching whatever owned-alias convention the target repo's own env config already establishes — check for one before inventing a new address). Never let the worker fabricate a plausible-looking address at the real domain: staging environments frequently share live transactional-email sending infrastructure with production, so a fabricated address still triggers a real send and a real bounce the human receives directly. Observed in practice: a worker invented a staging-verification address at the company domain, which bounced live against production's sender reputation even though the API call target was the staging host.
- **Assumption-verification checkpoint:** when a brief depends on a non-obvious technical assumption (column type, auth mechanism, API contract shape, determinism guarantee), include an explicit "verify X before building on it" line naming the assumption and how to check it (grep the type, read the config, run a one-liner).
- **Testable-seam extraction (untested-by-convention functions):** when a lane adds new behavior to a function the repo does not unit-test by convention — a CLI `cmd_*`/`cmdFoo` handler, a `main()`/entrypoint, an event-loop tick — the brief MUST require extracting that new behavior into an exported, independently testable unit (pure function or narrow module) in the SAME PR, with tests against the extracted seam. Do not let core logic land inline in an untestable function and wait for review to flag the coverage gap. State the acceptance-criteria-level tests the seam must carry. (Born from a real regression: the cross-repo selection/dispatch logic first landed inline in `cmdFeatureBuild`, forcing an extract-to-`planAndPartitionFeatureBuild` + retest fix cycle that Quine had to catch post-hoc.)
- **PR-body closing keywords — one per line:** briefs that instruct a lane to close issues state *"put each `Closes #N` on its own line — never comma-join (`Closes #1, #2` closes only #1; GitHub orphans the rest)."* (A create wrapper can auto-repair this, but author bodies correctly.)
- **Token-compression mode (technical lanes only):** if you use a compression plugin that shortens agent output, enable it when dispatching to code-producing lanes (`dorothy`, `tdd-test-writer`, `tdd-implementation`), and instruct the lane to return to normal prose before writing commit messages, PR bodies, or any user-facing artifact. Do NOT enable it for persona/strategy/prose lanes (`perlman`, `eiko`, `aristotle`, `retro`). Rule of thumb: output is code/diffs/tool-calls with a short summary → compression ON; output is prose judged on tone → OFF.

## Dispatch-pickup revalidation (added 2026-07-22)

An issue's cited facts can drift true between authoring and dispatch: line numbers, constant names/values, or described behavior may no longer match `develop` if the issue sat in `ready` for days while the code moved underneath it. three issues all kicked back citing a stale premise — the code had changed since the issue was filed, not the plan being wrong at write time. Before starting implementation on any issue that has been `ready` for more than ~3 days, spend the first few minutes of the lane spot-verifying each concrete claim (line number, constant name/value, function signature, the mechanism the issue assumes) against current `develop` — cheap up front, expensive as a kickback discovered mid-build. This is a lane-startup step, not a planning-time check (planning cannot see code that hasn't drifted yet); see `occam/issue-graph-preflight.md` → "Cross-repo, authority, and conflict pre-flight checks" for the checks that run at authoring time instead.

## Information-asymmetric unit-test lane

When a lane completes implementation via outside-in TDD (e2e/contract tests RED → implement to GREEN), dispatch the post-implementation unit-test pass as a **separate** lane to `tdd-test-writer` with the acceptance criteria + the public API surface (signatures, types, exported names) ONLY — never the implementation source. This structurally prevents unit tests from encoding what the code does (bugs included) rather than the contract; ambiguities the test-writer surfaces become contract clarifications. Caveat: signature-only works cleanly for pure functions and well-shaped modules; for stateful subsystems whose behavior depends on internal state machines, expand the envelope to include a behavioral spec (state diagram, invariants). The orchestrator decides when to expand. (Per an internal issue.)

## Parallelism & merge ordering

- **File collision check (intra-repo parallel):** before spawning parallel agents on the same repo, list modified files per lane. If two lanes touch the same file, serialize them or assign file ownership so only one lane edits each file. Check `git diff --name-only` before spawning a background agent; fold overlapping work into the foreground lane rather than spawning a duplicate.
- **Same-function edits → serialize:** worktrees solve stash pollution, not merge-conflict cost. If two lanes would edit the same function (not just the same file), merge lane A to develop, then branch lane B off the post-merge base. Parallelize only when edit regions are clearly disjoint (different classes, non-adjacent blocks, independent top-level functions). Grep the target function at plan time.
- **Serialize merges in same-base fanouts — across ALL operators:** when N PRs target the same base, merge serially with direct merges: merge PR 1 when CLEAN, wait `state == MERGED`, `update-branch` PR 2, wait for CI on its new head, merge, etc. Do not arm `--auto` on a PR that is not already CLEAN (armed-before-transition stalls — see SKILL Step 4). GitHub does not auto-update branches that fall to `BEHIND` after a sibling merges; CI cost of parallel arming is also N(N+1)/2 vs N. The serialization scope is every operator on the base, not just this session's lanes: pre-merge, run `gh pr list --base <base> --state open --json number,autoMergeRequest` — an armed PR from ANY author means wait-for-land before proceeding. With uniform agent identity, attribute lanes by branch prefix (`dorothy/`, and one per automated operator) and linked issue, not author.

## Workspace-lock handshake (acquire-or-worktree)

A unified workspace lock (`scripts/ws-lock.sh` in this bundle's convention — supply your own implementation) is one path-keyed "I'm working here" primitive. Acquiring it tells other agents to work in a worktree instead of this checkout, and marks the working tree off-limits to cleanup. If you already have a per-repo lock for an automated queue, keep it — the two have different readers (see "Automated-dispatcher lock" below).

- **Acquire before working.** From the checkout you intend to work in: `scripts/ws-lock.sh acquire <owner/repo> --lane <issue-ref>`.
  - If the **primary checkout** is free → it grants the primary. The JSON is `{"granted":true,"kind":"primary",...}`. Work there.
  - If the primary is held by a **live foreign holder** → ws-lock **auto-provisions a worktree** on a fresh `lane/<slug>` branch and returns its path: `{"granted":true,"kind":"worktree","worktree_created":true,"path":"<abs>",...}`. The lane MUST `cd` into the returned `path` and work there. Agents physically cannot improvise onto an occupied primary.
  - If worktree provisioning fails, ws-lock falls back to advisory BUSY: `{"granted":false,...,"holder":"<session>"}` (exit non-zero). Queue the lane behind the holder.
- **Heartbeat long lanes.** A lane that outlives the grace TTL refreshes liveness: `scripts/ws-lock.sh heartbeat <owner/repo> --path <abs>`. A live (PID-alive or recently-heartbeating) holder is never reaped.
- **Release at closeout.** `scripts/ws-lock.sh release <owner/repo> --path <abs>` (step in `closeout.md`). A crashed holder auto-frees only after its PID is dead AND the grace TTL since last heartbeat has elapsed — an abandoned lock never wedges the sweep.
- **Status before dispatching.** `scripts/ws-lock.sh status <owner/repo>` lists every lock (primary + worktrees) with holder + liveness. A live foreign lock on the primary means dispatch will auto-worktree; plan for it.
- The lock helper never blocks a lane: on a missing dependency it warns and continues.

### The hard cleanup rule (the guard the incident needed)

A 2026-06-20 a product repo closeout force-discarded another operator's uncommitted work in the shared primary checkout. The rule that prevents recurrence:

- **Never** run `git reset --hard`, `git checkout -f` / `--detach`, `git clean -fd`, `git branch -f`, or `git worktree remove` against a path that has a **live foreign lock**. A dirty working tree under another holder's live lock = **STOP and report** — never reset/clean/remove it.
- This applies to the **orchestrator's own closeout git ops too**, not just dispatched lanes. Before any destructive git op on a working tree, the cleanup helpers call `ws-lock.sh guard <path> <op>`, which exits non-zero and names the live holder when the path is foreign-locked. Do not route around a guard refusal — treat it as a STOP signal, escalate, and let the holder finish.
- Cleanup/closeout may only reset/clean/remove a tree with **no live lock** (free, your own, or dead+expired).

## Automated-dispatcher lock

The workspace-lock handshake above guards the working **tree** — it keeps other operators (and cleanup) off a checkout while a lane runs. If you also run an automated build queue that dispatches into repos on its own, that is a **different lock with a different reader**, and a local orchestrator lane needs both.

The failure this prevents: your queue has no way to see an in-session agent lane. A worktree is a sibling path, so a CWD-based presence check misses it; an in-flight-dispatch store only ever holds the queue's *own* dispatches. Neither auto-detects a lane you spawned. The issue-level `building` label is necessary but not sufficient — it marks the *issue*, not the *repo*, and a sweep may legitimately strip it.

- **Acquire before spawning any local worker lane**, scoped to the expected lane duration plus a margin. A short presence heartbeat is the lighter alternative but ages out mid-lane, so it only suits short lanes unless re-touched.
- **Verify it took.** A silent failure here reproduces the exact bug this rule exists to prevent — STOP and report if the lock does not read back as held.
- **Multi-lane shared repo — the easiest way to get this wrong.** The lock is per-**repo**, not per-lane. Acquire **once** for the repo and release only when the **LAST** lane on it closes. Do NOT let lane A's closeout unlock a repo lane B is still building; when a later lane starts on an already-locked repo, extend the expiry rather than re-acquiring.
- **Cross-repo lanes:** one lock per target repo touched.
- **Release at closeout.** The expiry is the crashed-session backstop, not the intended release path.
- **Keep both protections.** The repo lock and the `building` label have different readers and neither supersedes the other. Take the lock AND re-check the issue's labels after dispatch, re-applying `building` if it was stripped.

## Worktree isolation

### Flattened-your checkout root hook mechanism 

After your checkout root was flattened it is no longer a git repository, so Agent `isolation: "worktree"` fails with `not in a git repository and no WorktreeCreate hooks are configured` — and a lane whose cwd is the your checkout root root would otherwise create a **stray worktree at the root**. `WorktreeCreate`/`WorktreeRemove` hooks now bridge this:

- **Registered** in `.claude/settings.json` → `hooks.WorktreeCreate` / `hooks.WorktreeRemove`, pointing at your worktree-create hook and your worktree-remove hook. Loaded by the harness **at session start** — a fresh registration requires a session restart before live dispatch picks it up.
- **Target-repo resolution rule (the robust signal):** the create hook derives the target repo by walking up from the dispatching agent's `cwd` to the nearest real git repo (`git -C <cwd> rev-parse --show-toplevel`). It creates the worktree UNDER that repo's checkout at `<target>/.claude/worktrees/<name>` (mirroring the default convention), branch `worktree-<name>` unless the harness supplies one, prints the actual path to stdout, exits 0.
- **Guard (fail loud, never stray):** if `cwd` resolves to no git repo (e.g. it is the your checkout root root, post-flatten), the create hook **exits non-zero with a clear stderr error** and creates nothing — a misconfigured lane fails loudly instead of polluting your checkout root root. So for a worktree-isolated lane to succeed, **the Agent's cwd must be inside the target repo's checkout** — dispatch it there.
- **Teardown:** `WorktreeRemove` runs `git worktree remove` (force-fallback if dirty/locked) then `worktree prune`; tolerates an already-gone worktree; non-blocking.

### Cross-repo gate — the :139 prohibition, made executable

The bold prohibition in "Cross-repo lanes" below (do **not** use `isolation: "worktree"` cross-repo) was read in-session and violated anyway — prose does not bind. your worktree-create hook now **enforces** it at the event that actually knows a worktree is being cut, rather than leaving it to attention:

- The lane's declared `target_repo` (brief-contract field above) reaches the hook via the `WORKTREE_TARGET_REPO=<owner/repo>` env var the orchestrator sets for an `isolation: "worktree"` dispatch.
- The hook resolves the **session** repo's `origin` slug — the checkout it walks up to from the dispatching agent's cwd, i.e. the repo the worktree would actually fork from. If a `target_repo` is declared and its slug differs, the hook **blocks, creating nothing**, and prints the dispatch-briefs.md:139 text as the error.
- **Not prompt inference (AC3):** the gate never regexes the prompt for repo slugs — that is the same unreliable-inference failure class it guards against. It compares the declared target against live git state.
- **Permissive wherever intent is unknowable, so legitimate flows never trip:** no `WORKTREE_TARGET_REPO` set → proceed (ordinary intra-repo isolation); session repo has no `origin` → proceed (nothing to compare against). The **hand-provisioned per-lane escape** (below, dispatch-briefs.md:140) never reaches this hook at all — it uses `git worktree add` dispatched **without** the isolation flag, so there is no `WorktreeCreate` event to gate.

**No-worktree fallback — the serial-in-primary-checkout policy:** a prior change shipped the hook mechanism above, so it is the default, not an unconfirmed path. Reach for the no-worktree fallback only when isolation is positively confirmed infeasible for a given lane (e.g. the hook is unregistered this session and a restart isn't available) — run **one lane per repo serially in the target repo's primary checkout, no worktree**, safe precisely because no concurrent agent touches that repo for the lane's duration. This is the policy used successfully for an internal issue, back when the hook path was still unconfirmed; do not reach for it by default now.

- **Isolate every implementation lane** (parallel OR serial) unless you have positively confirmed no other agent can touch the repo for the lane's duration. Any parallel batch of 2+ on the same repo MUST use isolated worktrees: `git worktree add /tmp/<repo>-<lane-slug> -b <feature-branch>`; the agent `cd`s in for all work; the orchestrator runs `git worktree remove` at closeout. The hazard is not only sibling lanes — external concurrent agents (an automated maintenance queue, parallel sessions, scheduled jobs) can `git checkout` the shared checkout out from under the agent. Stash-audit-between-batches is a weaker fallback, only when worktrees are infeasible.
- **pwd-confirm + STOP-on-mismatch:** the brief requires the agent to (1) `pwd` at task start to confirm CWD matches the assigned worktree; (2) STOP IMMEDIATELY on mismatch — do NOT improvise onto the primary checkout, do NOT `git checkout` another branch, do NOT edit; emit a completion report naming the mismatch and let the orchestrator re-dispatch; (3) treat any `git checkout <feature-branch>` against the primary repo path as forbidden.
- **Branch-already-checked-out STOP:** if the target branch is checked out in a DIFFERENT worktree (`error: '<branch>' is already checked out at '<other-path>'`), STOP, name the other worktree in the report, and let the orchestrator either free it (`git worktree remove -f -f <other-path>`) and re-dispatch, or re-assign the lane to that worktree. Never silently `cd` into the other worktree.
- **Path discipline inside the worktree:** the built-in `Read`/`Edit`/`Write` tools honor whatever absolute path you pass — they do not know which worktree you're in. Brief: `export WORKTREE=$(pwd)` as step 0 after the pwd-confirm, and use `$WORKTREE/<rel-path>` or relative-from-CWD paths for every Read/Edit/Write. Forbid absolute paths rooted outside the worktree in instructions and in the agent's tool calls.
- **Base verification (non-default-base lanes):** `isolation: "worktree"` does not reliably inherit the parent's current branch. For lanes targeting a non-default base (sprint branch, epic branch), the brief requires as FIRST action: (1) `ls`/`cat` a file the agent can verify by content (e.g. "`ls <dir>/` MUST include `<base-only-file>`"); (2) if missing, self-correct `git fetch origin <base> && git checkout origin/<base> -B <feature-branch>`; (3) only then create the feature branch. Name actual files present on the intended base but not adjacent bases — generic "check branch name / git log" tests are too easy to fool.
  - **Align-base-with-default (Phase 0 corollary):** when an epic deploys off a long-lived branch other than `develop`, dispatch a Phase 0 step that merges `origin/develop` into the long-lived branch BEFORE spawning lanes, so a downstream `git checkout origin/<long-lived> -B ...` is a fast-forward, not a content swap.

## Orchestrator-inline cross-repo work (persistent-cwd discipline)

The pwd-confirm rules above govern dispatched agent lanes. The orchestrator's
OWN Bash shell has the same hazard: CWD persists across tool calls, so a `cd`
into another repo for a quick sub-task silently re-anchors every later
relative-path operation (two incidents in two days: worktrees created off the
wrong nested repo 2026-06-11; a feature branch created in the wrong repo
2026-06-12).

- Prefer `git -C <abs-path>` (and absolute paths in file/search tools) for any
  operation in a repo other than the workspace root — avoid `cd` entirely.
- When a command must `cd` into another repo, contain it in a subshell
  (`( cd <repo> && … )`) or end the same command by returning to `$WORKSPACE`.
- Before any branch create/checkout, `git worktree add`, or
  `isolation: worktree` dispatch: confirm `git rev-parse --show-toplevel`
  matches the intended repo.
- After any foreign-repo `cd`, pass absolute paths to search/edit tools until
  the shell is verifiably back at `$WORKSPACE` — relative globs resolve against
  the drifted CWD and fail confusingly (or worse, succeed against the wrong
  repo).

## Cross-repo lanes

- **Do NOT use Agent `isolation: "worktree"` cross-repo** — it allocates the worktree relative to the PARENT process's repo, landing it under the wrong repo every time. Instead, the brief instructs the agent to `cd <target-repo primary checkout>` and create the feature branch there. Worktree isolation only protects against intra-repo collisions; cross-repo it offers no value and actively misleads.
- **2+ lanes on ONE cross-repo target → hand-provision a worktree per lane:** the cd-into-primary-checkout rule isolates a *single* cross-repo lane, but back-to-back lanes on the SAME target serialize on that one checkout — lane 2 lands on lane 1's still-open branch + unpushed commit and trips the concurrent-operator STOP (correct, but costs a re-dispatch). When you know 2+ lanes will hit the same cross-repo target, provision a dedicated worktree per lane YOURSELF before dispatching: `git worktree add -b <feature-branch> <repo>-<lane-slug> origin/develop`. Dispatch each agent at that absolute path WITHOUT the `isolation: "worktree"` flag (still mis-anchors to the parent repo), with the brief: *"work ONLY at <path>; your branch is already correct — do NOT `git reset --hard` or `git checkout` another branch; use file tools that honor your own working directory, not any tool that resolves paths against the orchestrator's checkout."* Prune each with `git worktree remove --force` at closeout.
- **Pre-resolved target path:** embed the target repo's absolute path verbatim in the brief — agents should not have to `find` for it. Resolve it from whatever repo registry or workspace-context file your setup keeps. Brief: `cd <resolved/path>` with the exact path, not a placeholder. Watch aliased repos whose directory name differs from their GitHub slug, or that live nested under a parent project directory.
- **Repo-identity check:** the brief requires `gh repo view --json name -q .name` to match the target as the agent's FIRST action; STOP if it does not.
- **Concurrent-operator pre-flight:** because cross-repo lanes work in the primary checkout (no worktree), immediately after the repo-identity check run `git status --porcelain` and `git branch --show-current`. If the tree is dirty OR the branch is not the expected base (`develop` unless stated), STOP and report — do NOT branch, stash, or commit over another operator's in-progress state.
  - **Expected-debris allowlist:** if your tooling generates per-repo local artifacts that appear dirty in every checkout, they are NOT a concurrent-operator signal. Enumerate them explicitly in the brief's allowlist and STOP only on a dirty path OUTSIDE that set — an unenumerated allowlist means either false STOPs or, worse, a habit of ignoring dirty state.

## Supervision

- **Pre-redo gh-pr-list gate:** before re-dispatching or redoing work assigned to a background agent that has gone silent for >5 minutes, run `gh pr list --repo <owner/repo> --state all --search '<branch-or-issue-keyword>'` AND `git ls-remote origin '<branch-pattern>'`. If a PR exists (OPEN or MERGED) or the branch exists with commits ahead of develop, the agent succeeded — your job is verification, not redo. Silence is a "wait or check" signal, not a failure signal.

## Situational lane shapes (decomposition, extraction, campaigns)

Give the brief extra scrutiny when the lane's SHAPE — not its subject — is unusual: standing up a new repo, extracting a package for publication, extracting a repo, **any other decomposition lane in which code moves away from the assets it references**, or fanning out a large mechanical migration. None of these fires on an ordinary in-repo dispatch.

## Cross-cutting change rules

- **MCP-tool removal must hard-block the host IPC path:** a PR removing an MCP tool that has a host-side IPC handler MUST either delete the handler or add a warn-and-reject guard refusing direct IPC writes for the removed action. "Leave it as dead code for rollback" is unsafe — agents can bypass the MCP surface by writing the IPC request JSON directly with `Write`. For rollback capability, use a feature flag that defaults to rejecting, not live dead code.
- **Checkout in a `pull_request` workflow that runs repo-local code must pin to the trusted base:** when a brief adds `actions/checkout` to any workflow triggered by `pull_request` (incl. dependabot/bot-authored PRs) and a later step executes repo-local scripts or composite actions (`./.github/actions/<name>`, `scripts/*`), the brief MUST specify `ref: ${{ github.event.pull_request.base.sha }}` and `persist-credentials: false` on the checkout up front. A bare checkout fetches the PR merge ref, and `.github/actions/**` is NOT covered by the workflows token scope — a poisoned PR branch can rewrite the local action and exfiltrate every secret later steps load (secret-manager tokens, App keys). Review-time rescue is not the control; the brief is.
- **Local composite action requires `actions/checkout`:** a lane adding or migrating workflows to `uses: ./.github/actions/<name>` must pre-flight audit consumer workflows missing checkout: `grep -L "actions/checkout" $(grep -rl "./.github/actions" .github/workflows/)`. For each, add a full `actions/checkout@v4` or a sparse-checkout limited to `.github/actions/` (sparse for dispatch/status-only workflows). Without checkout the runner cannot resolve `action.yml`; PR CI passes (workflow files don't fire on PR) but the first push to a trigger branch fails with `Can't find 'action.yml'`.

## Per-lane execution (repo-local safety)

- Set the tool `workdir` to the target repo; read repo-local `AGENTS.md` before edits; keep commits, PRs, and evidence repo-local; never mix repos in one commit or PR.
- **Stash check (lane start):** run `git stash list` before the first edit. Treat every stash as prior-agent debris unless you created it this session. Triage each per the single default: a stash whose content is provably already on a merged branch is droppable; everything else gets parked to a branch, not dropped. "Provably" means you diffed it.
- **Package-manager discipline:** check the committed lockfile before any install. `package-lock.json` → `npm ci`; `yarn.lock` → `yarn install --frozen-lockfile`. Never run the other tool — it regenerates the wrong lockfile as an untracked file and can resolve a different dependency graph than CI. State the rule explicitly in any JS/TS brief.
- **Verify-list parity:** before writing a lane brief's local-verify list, enumerate the repo's CI job steps (`ci.yml` or equivalent) and include every step that is runnable locally — bundle/size budgets (`yarn size`), coverage gates, contract checks — not just lint/typecheck/test/build. A lane that verifies a subset of CI ships avoidable gate failures — a lane that passed lint/typecheck/test/build locally and then failed CI on an unrun bundle-size budget is the canonical example.
- **Dependabot alert triage (cleanup lanes):** for each open alert, decide runtime exposure in THIS repo's actual environment (is the vulnerable path reachable from a request, a scheduled task, or a build output that ships to users?). If not (transitive through a lint/test/build tool in a static-export frontend; a server advisory in a repo with no server runtime), dismiss: `gh api -X PATCH /repos/<owner>/<repo>/dependabot/alerts/<N> -f state=dismissed -f dismissed_reason=not_used -f dismissed_comment="<≤280 chars why unreachable>"`. Valid reasons: `not_used`, `tolerable_risk`, `fix_started`, `inaccurate`, `no_bandwidth`. Only file a GH planning issue when exposure is real; group by upstream package family.

## Read-only status/reporting lanes

- Prefer a single scripted per-repo hygiene summary (start/end cleanliness, origin sync, promotion linearity, safe checkout state, failing checks on develop/staging/main) over ad-hoc `git`/`gh` calls per lane — one deterministic read is cheaper and more consistent than N improvised ones.
- Use `scripts/repo_cleanup_triage.sh --repo-path <repo-path> --mode status --skip-fetch --skip-gh` when a worker needs only the repo-local engine layer.
- Keep prioritization local to each repo lane; the parent report preserves that order with one section per repo and no cross-repo re-ranking.

## Per-lane review flow

- **User-facing:** Eiko specifies design intent → Dorothy implements → pushes + opens PR → CI runs → Eiko verifies (optional, Occam decides) + Quine reviews.
- **Non-user-facing:** Dorothy implements → pushes + opens PR → CI runs → Quine reviews.
- Dorothy owns the full implement → test-locally → push → CI-green → PR cycle; diagnoses and fixes CI failures with `gh-actions-utils`.
- Quine reviews after the PR is up and CI is green.
- **Default Quine to one reviewer per PR (parallel per-lane), not a single batched pass over multiple diffs.** A batched review dilutes attention across N diffs in one context and risks cross-diff bleed; parallel per-lane gives each diff full, undiluted attention. Batching is a token-economy trade, not the default — opt into it ONLY when every diff in the batch is genuinely trivial: all diffs <~15 LOC, same repo, `moscow:could`/`should` (not `must`), and no shared file between them. *(Evidence: 2026-07-10 Wave-P sweep — switching the remaining 7 lanes from a batched single-pass to parallel per-lane directly caught two real MUSTs — a dead-PID lock-reaper TTL-deletion bug and an unplanned-MUST escalation gap — that a batched pass had already missed on the first 3 lanes.)*
- **Verify-by-running (between CI-green/Quine and merge):** for a lane with a behavioral surface, drive the affected flow and observe the change working before merge — graded by runnability (cheaply-drivable → run via `verify` / `run`; heavy / multi-service → satisfied by the staging Playwright E2E gate; no runtime surface → exempt). "Tests pass" is not observation. Full grading + the hard line: `occam/verify-by-running.md` (Gate 3).
- Merge to `develop` after the QA triage gate passes **and the verify-by-running gate is satisfied**. Promote to `staging` via the Ship-to-staging routine. Keep `main` human-gated. Each lane completes Ship-to-staging before it is closed — merging to develop is an intermediate step, not lane completion.
