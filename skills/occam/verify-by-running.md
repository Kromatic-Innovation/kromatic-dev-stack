# Verify-by-running gate

Companion to `occam/SKILL.md` Gate 3. **Read this when you are deciding whether
a lane may merge** — it grades the observation requirement by runnability,
including what qualifies as no-runtime-surface and the inert-component flag that
case carries, and states the one hard line.

Relocated verbatim from `occam/SKILL.md` by an internal issue (context diet). No rule
text was altered in the move. `occam/dispatch-briefs.md` points here for the
full grading behind the closure contract's verify-by-running observation.

- **Verify-by-running gate (between CI-green/Quine and merge).** *Drive the affected flow end-to-end and observe the change actually working* before the lane is declared done — this is NOT "run the test suite." Per the `verify` skill's own framing, exercise it end-to-end and observe behavior, not just tests or typecheck; running `npm test` is not running the repo. Unit tests encode expected behavior; they don't catch wiring/integration/environment gaps that only surface when the real flow runs. The expectation is **graded by runnability**, not a blanket hard gate:
  - **Cheaply drivable in-session** (agent skills, CLIs, single-service apps, pure Node/TS) — verify-by-running is the **expected default**: drive the affected flow via the `verify` / `run` skill and observe the change working before merge. A silent skip here is a real miss.
  - **launchd/cron jobs — `loaded` is NOT `runs`.** A job showing `loaded` in `launchctl list` (or `state = running`) proves only that launchd accepted the plist, not that it executes from the new location. Drive one real run — kickstart the job, or run its producer `--dry-run` that reads live state (e.g. `cron-fleet-watchdog --dry-run`), from the *migrated* path and confirm a clean exit + fresh output. A manual shell invocation does NOT count: it bypasses the plist's `WorkingDirectory`/env and succeeds even when the installed job cannot spawn. Tell: `last exit code = 78: EX_CONFIG` with empty job logs (and `bash -x` yielding zero trace) is a launchd spawn-setup failure → confirm the plist's `WorkingDirectory` and the parent dirs of `StandardOutPath`/`StandardErrorPath` resolve to existing paths. When migrating a job's files, repoint EVERY absolute path in the plist (`ProgramArguments`, `EnvironmentVariables`, `WorkingDirectory`, std-path dirs), not just the obvious ones.
    - **`exit 0` + fresh output is NOT sufficient — diff the run against the last known-good pre-migration run.** A repointed job can spawn correctly, exit `0`, and write a fresh, clean-looking log while doing none of its work: a script whose own error handling misattributes an internal defect to an external dependency will report a benign skip and keep cron-health green. Capture the job's last pre-migration output BEFORE cutting over, then compare the post-migration run against it — a run that changes from doing-the-work to skipping-the-work is a regression no matter how clean its exit code. Read the WHOLE log, not the last line: the real tell sits above the reassuring one. Confirmed 2026-07-24: a repointed `calibration-resolver` passed every structural gate — lint, env parity, `bootstrap`, `exit 0` — while logging `wait_for_tcp_port: command not found` and then "dev-postgres not reachable … not a resolver bug … exit 0 so cron-health does not flag a logic failure." The previous day's run logged `resolver OK`; that one-line diff was the only honest signal.
    - **A conditional path that has never fired is NOT verified by deploying it.** The two rules above cover a job that runs; this covers a branch *inside* one that never gets asked to. A tier gated on an input that has not arrived (a bounce handler, an error path, a rare-verb dispatch) can be correct, deployed, and dead for weeks with every structural signal green — because none of them distinguish "works" from "has never been invoked." When a cutover touches such a path, either drive a real input through it (replay a captured payload against the DEPLOYED binary, not a test fixture) or state plainly that the path is unexercised and say what would exercise it. Confirmed in practice: the bounce tier passed plist lint, env parity, `exit 0`, a full-log read AND a real-DSN replay through `detectBounce` — yet the triage log shows **zero** `bounce` actions in its entire history, against an inbox that demonstrably received matching DSNs. Deployed, correct, and never once invoked.
  - **Expensive / multi-service / infra-dependent** (e.g. a frontend that needs its API service + Docker + DB) — a local run is a **suggestion, not required**; the requirement is **satisfied instead by the existing Ship-to-staging Playwright E2E gate** (GATE 4 staging / GATE 6 prod), which drives the real flow post-deploy. Do not force an infeasible local stack.
  - **No runtime surface** (pure skill-doc/rules/markdown, config-only, or a pure library/engine with no caller) — exempt from the *run*. A library/engine with no caller instead triggers the inert-component flag (its wiring becomes a blocking dep), rather than being run.
  - **The one hard line:** a change WITH a behavioral surface must never go silently CI-green → merge with **zero** observation of its behavior. Observation can be a local run, a staging E2E pass, or an explicit one-line statement of why neither was possible — but not nothing. The worker records HOW in its completion report (see `occam/dispatch-briefs.md` closure contract).
  - **Never conclude absence from `cmd | grep`.** A pipeline discards the producer's exit status by default — `cmd | grep pattern` returning nothing is reported by `$?` as grep's exit code, not `cmd`'s. That empty result is ambiguous between two completely different worlds: "`cmd` ran and found nothing" (clean) and "`cmd` never ran, or crashed before producing output" (unknown). Verification-of-absence is the highest-risk form of this gate, because absence is exactly what a broken command *also* produces — a stack trace piped through a narrow `grep -i` filters down to nothing just as cleanly as a genuinely clean report does. Do not trust an empty result from `cmd | grep` unless one of:
    - **`set -o pipefail` plus an explicit exit-code check of the producer.** `set -o pipefail; cmd 2>&1 | grep -i pattern; ec=${PIPESTATUS[0]}` (bash) makes the pipeline's exit status reflect any failing stage, and `${PIPESTATUS[0]}` isolates the producer's own code so a `grep` no-match (exit 1) doesn't get conflated with a producer crash. Check `ec` before trusting the empty grep result.
    - **A positive control proving the pipe is live.** Before trusting an empty result, run the same pipeline against input known to match (a fixture, a deliberately-planted line, or a prior known-bad state) and confirm it reports non-empty. If the control doesn't fire, the pipe is dead and the real run's silence is meaningless.
    - **Worked example:** a session verifying a cleanup had landed ran `fleet doctor 2>&1 | grep -i "google-workspace\|bak\|stray"`. It returned nothing and was reported "clean." In fact `fleet doctor` (`node bin/fleet.mjs`) had exited `MODULE_NOT_FOUND` — wrong path, empty `dist/`, no `fleet` binary on `PATH` — and the `grep` had filtered a Node stack trace down to nothing indistinguishable from a clean report. It was caught on self-recheck and re-verified at the authoritative source: `find ~/Library/LaunchAgents -maxdepth 1 -type f ! -name '*.plist'` → empty. That is the correct shape.
  - **Prefer querying the authoritative source directly over filtering a reporter's output.** `fleet doctor` is a *reporter* — a layer between you and the thing you actually care about, and every layer is a place the signal can go silently dead (crash, wrong path, stale cache, permissions). Where the underlying state is directly queryable, ask it instead of asking a tool that summarizes it: the `fleet doctor` false-green above was caught precisely by dropping the reporter and re-querying the filesystem directly (`find ~/Library/LaunchAgents -maxdepth 1 -type f ! -name '*.plist'`) — ask the thing itself, not a reporter about it.
